# rate limiting
    1. API Gateway Rate Limiting
────────────────────────────────────────────────────────────────

Purpose:
Protect the Gateway from request flooding, accidental CLI loops,
or malicious clients sending excessive API requests.

Why?
Without a request limiter, a client can continuously send backup
requests, consuming unnecessary Gateway and Redis resources before
they even reach the backup pipeline.

Implementation:
• Redis + rate-limiter-flexible
• Applied as middleware before routing requests
• Limit based on API Key / User ID

Example Limit:
100 requests/minute per API Key

Action on Limit Exceeded:
• Return HTTP 429 (Too Many Requests)
• Request is rejected immediately


2. Backup Orchestrator Resource Limiting (Most Important)
────────────────────────────────────────────────────────────────

Purpose:
Prevent expensive backup operations from overwhelming the system.

Why?
A backup job is CPU, memory, disk, and database intensive.
Instead of limiting API requests, the Orchestrator limits how many
backup jobs the system can safely process.

Checks Before Enqueueing:

✓ Active Running Jobs < MAX_RUNNING_BACKUPS

✓ Queue Size < MAX_QUEUE_SIZE

If both checks pass:
    → Create Backup Metadata
    → Push Job to BullMQ

Otherwise:
    → Reject the backup request with an appropriate error.

Example:

Running Jobs = 3
MAX_RUNNING_BACKUPS = 3

↓

Reject New Backup

Queue Size = 50
MAX_QUEUE_SIZE = 50

↓

Reject New Backup


3. BullMQ Queue
────────────────────────────────────────────────────────────────

Purpose:
Buffer incoming backup requests instead of executing all of them
immediately.

Why?
Executing every backup instantly can overload the database,
CPU, and storage. BullMQ acts as a buffer and schedules jobs
for execution when workers become available.

Job States:
• Waiting
• Active
• Completed
• Failed
• Delayed (Scheduled Backups)

Implementation:
BullMQ Queue (Already Implemented)


4. Worker Concurrency Control
────────────────────────────────────────────────────────────────

Purpose:
Limit the number of backup jobs executing simultaneously.

Why?
Running too many backups in parallel can exhaust CPU, RAM,
database connections, and disk I/O.

Implementation:

new Worker(queue, processor, {
    concurrency: 3
})

Meaning:
• Maximum of 3 backup jobs execute simultaneously.
• Remaining jobs stay in the BullMQ waiting queue.


5. Restore Lock (Distributed Lock)
────────────────────────────────────────────────────────────────

Purpose:
Ensure that only one restore operation is performed on the same
database at any given time.

Why?
Running multiple restores on the same database simultaneously
can lead to inconsistent or corrupted data.

Implementation:
Redis Distributed Lock

Key Format:

restore:<database-name>

Flow:

Acquire Lock
      ↓
Perform Restore
      ↓
Release Lock

If Lock Already Exists:
• Reject the restore request.
• Inform the user that another restore is already running.


6. Scheduler Execution Guard
────────────────────────────────────────────────────────────────

Purpose:
Prevent duplicate scheduled backups from executing at the same time.

Why?
If a scheduled backup is still running when the next scheduled
execution starts, duplicate jobs may be created for the same
database.

Implementation:

Before creating a scheduled backup:

✓ Check if another backup for the same database is already running.

If Running:
    Skip Current Execution

Else:
    Create New Backup Job

Result:
Only one scheduled backup for a database can run at a time.
